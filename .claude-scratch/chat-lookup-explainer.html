Design review explainer · docs/designs/sta-9590-chat-lookup-design.md

Finding a chat's workspace without reading every tab

Native chat keeps asking "which workspace owns this terminal tab?" Today it answers by walking every tab in every workspace, every time the store changes. The design makes it ask an index that already exists.

ELI5

Picture a library with 1,200 shelves and 2,600 books. Every time anyone in the building moves a bookmark, 20 librarians each walk every shelf to find which shelf holds "book #t7". The fix: there's already a card catalog. Add one more column to it ("first shelf this book appears on, and which slot"), then go straight to that slot and read the book that's actually there right now.

REQUIREDIndex-backed tab lookup

Add a "first location" query to the existing terminal owner index. Route native chat's lookup through locateTerminalTab. Same answers, far less work.

OPTIONAL · MEASURE FIRSTOther callers

AI Vault path matching, structured tabs, title sync, sidebar, status routing. Each ships only if counters show it's still hot.

NOT THIS TICKETHost identity

Making tab IDs host-qualified and enforcing one owner per tab belongs to the runtime-management refactor.

The design adds no new store, subscription system, polling, persisted field, IPC method, or wire format.

Background

How terminal tabs are stored

The renderer store keeps tabsByWorktree: an object whose keys are workspace IDs ("buckets") and whose values are ordered arrays of TerminalTab rows. This is the canonical source. It's the one recovery, budgets, and close logic all read from.

To answer "who owns t7?", the old code loops over buckets in key order and checks each row's id until it finds a match. Highlighted: the row it's looking for.

There's a second, separate map, unifiedTabsByWorktree, which drives what the tab bar shows (presentation). It looks similar but is a different source. The design insists you never answer "does this terminal exist?" from it. Here's why.

The problem

What's slow today

Native chat uses a Zustand selector to find its owner workspace. Zustand re-runs every selector on every store publication, even ones that have nothing to do with tabs: an agent status change, a terminal title tick. Returning a string avoids a React re-render, but the scan inside the selector still runs.

Target tab lives in a late bucket. Each square is a workspace, each bar a tab.

That multiplication is illustrative arithmetic built from historical reports (1,000–1,200 workspaces, 2,400–2,600 tabs). The design is explicit: nothing here has been measured on this checkout, and the mounted-chat count is unknown. The real number gates whether optional stages ship.

The required change

The fix, in one picture

Reuse what exists. terminal-tab-owner-index.ts already tracks bucket identity and tab membership incrementally. Teach it to also remember where each tab first appears, then put it behind the existing locator.

// "The one scan over tabsByWorktree."
for (const [worktreeId, tabs] of
     Object.entries(tabsByWorktree)) {
  const index = tabs.findIndex(
    (c) => c.id === tabId)
  if (index !== -1)
    return { worktreeId, index,
             tab: tabs[index] }
}
return null

const loc = ownerIndex

const tab =
  tabsByWorktree[loc.worktreeId][loc.index]

WHY POSITIONS

The catalog stores "shelf 41, slot 2", not a photocopy of the book. If someone replaces the book with a newer edition (a title change, a recovery update), you still read the new one. A cached copy would hand you stale recovery data, which is exactly the bug class this code has hit before.

What makes this tricky

Two traps the design steers around

Trap 1: who wins when a tab ID appears twice?

In a correct world, one tab has one owner. But legacy data can contain the same bare ID in two buckets (for example, local and remote hosts both issuing t7). Different callers today pick different winners. A "faster" lookup that quietly changes the winner is a behavior change.

FIRST WINS → ws-local

Native chat, locateTerminalTab, agent-status routing. The new query must match this.

LAST WINS → ws-ssh

Existing owner index (getOwner), sidebar attribution, title sync's flat map. Must stay unchanged.

This is why the design rejects simply swapping in the existing getTerminalTabOwnerWorktreeId: it's last-wins, native chat is first-wins. The index will maintain both answers from one membership pass. Neither answer makes duplicates valid; fixing that is runtime-management's job.

Trap 2: the tab bar is not the source of truth

USE

tabsByWorktree

Canonical rows. Carries the recovery generation and the remount budget ledger. Recovery remount, budget settlement, close admission, and native-chat exclusion must all resolve the same row.

DON'T USE FOR EXISTENCE

unifiedTabsByWorktree / getTab

Presentation. A past change answered recovery from here; every remount erased the budget it had just spent, so the restart cap never held (crash b5cfc6ca). The comment in terminal-tab-location.ts records it.

GOTCHA

The shared index remembers only one source map. If someone alternates A → B → A (title sync compares current vs previous state), it diffs every time. The design calls this out as something to measure, and forbids "fixes" like caching by mutable-map identity or an unbounded per-snapshot cache.

Optional stage · only if measured hot

AI Vault: matching a session's folder to a workspace

AI Vault lists past agent sessions and labels each with the workspace it ran in, by matching the session's cwd against workspace paths. Today each session filters every candidate path. The proposal: build a map per host of normalized root → best candidate, then for each session check only the cwd and its parent folders.

Index for host "local"
Probes, deepest first

Tie-break rules (unchanged from today)

  1. Longer original normalized candidate path wins. A WSL alias's depth doesn't count as its length.
  2. Same length: a current path beats a prior (renamed-from) path.
  3. Still tied: original candidate order (stable sort).

Also preserved: path normalization from cross-platform-path.ts (Windows folds case, POSIX doesn't; WSL UNC normalization is not idempotent, so normalize once), slash-boundary matching so /code/app doesn't match /code/application, and the title/branch fallback for sessions with no cwd. Known limitation left alone: the "current" badge compares only worktreeId, not host. That fix is a separate review.

Proposed order

Delivery order

  1. Characterize current behavior

    Differential and count fixtures beside native-chat lookup tests, using real store publications and real selector consumers. Coordinate the shared owner-index API with STA-7552.

  2. First-location extension (the actual deliverable)

    Change the owner index, the locator, and the native-chat file-link lookup. Recovery callers unchanged. No PTY edits. Complete on its own.

  3. Structured tabs and path fallbacks

    Typed lookup filtered to agent-session before matching, not after. Keep terminal-before-structured order for legacy callers.

  4. AI Vault matching

    Smallest measured improvement first (host/cwd grouping), then the ancestor index if distinct-cwd counts still justify it.

  5. Secondary callers

    Title sync and sidebar summary, only with before/after counts.

  6. Packaged validation and gate registration

    Experimental count gate in config/reliability-gates.jsonc; promote after red/green evidence and stable CI.

Acceptance

How we'll know it worked

Tests count work by observing inputs (keys enumerated, bucket reads, row ID reads), not by timing. Scales: 100 and 1,200 buckets, 240 and 2,600 tabs, 20 mounted chats, multiple hosts. A deliberate old-scan control must fail the gate.

Packaged validation runs hidden (ORCA_BACKGROUND_LAUNCH=1, CDP screenshots only) across macOS, Linux, Windows, WSL, SSH, and Git/folder/floating workspaces. A lower scan count isn't claimed as lower typing latency until end-to-end measurement shows it.

For the reviewer · my reading, not from the doc

Things worth pushing on

Is the required stage small enough to be obviously safe?

It's three files, but the owner index is shared with STA-7552 and PTY code. Ask for the exact API addition and confirm existing last-wins results are untouched by construction, not just by tests.

First-wins inside a bucket vs across buckets.

"First" must mean first outer key in JS enumeration order, then first row in that bucket. Check the index tracks within-bucket duplicate positions, not just bucket membership.

Metadata adoption trusts the producer.

Title adoption skips re-reading rows, assuming IDs and order didn't change. Confirm every adoption caller still proves that, because positions (not just membership) now depend on it.

A→B→A churn.

One remembered source plus title sync comparing previous/current could make the index diff on every write. Is there a counter for this in stage 1, or is it discovered later?

Two selectors per chat.

Stage 2 fixes the terminal path in both selectors, but structured chats still pay a structured scan unless stage 3 ships. Is that residual acceptable?

No measurements yet.

All motivating numbers are historical. Stage 1's count fixtures are the first real evidence; decide up front what count would justify the optional stages.

Doc length vs deliverable.

About 240 dense lines for a three-file change. Most of it guards against scope creep and identity mistakes. Consider whether the PR description needs only the "Decision" and "Independent delivery contract" sections.
